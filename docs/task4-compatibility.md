# Compatibilidad agregada en la tarea 4

Resolver una referencia para TeaVM no demuestra compatibilidad completa con el JDK ni ejecución del juego. Los puentes siguientes son propios; usan firmas y metadatos de la copia externa. Las fuentes del juego no se copian al repositorio.

## Límites explícitos

- JMX, contadores de GC/JVM, procesos, listeners TCP/HTTPS, DNS del sistema, linker/ABI anfitrión y carga de bibliotecas no se simulan. Fallan con errores descriptivos. OperatingSystemMXBean informa navegador, arquitectura Wasm y hardwareConcurrency; no describe el SO anfitrión. La ausencia de compilación JIT usa el null previsto por CompilationMXBean.
- ObjectInputStream no implementa serialización Java; PhantomReference no implementa el ciclo de limpieza nativo; sus rutas fallan explícitamente. Arena.ofAuto, StructLayout.varHandle y reinterpret con cleanup siguen pendientes.
- Metadata genérica de reflexión y detección de clases anónimas todavía no están enlazadas. StackWalker rechaza explícitamente los frames FakeClass de TeaVM porque este modo no aporta metadata Java simbolizada. Estas áreas no cuentan como compatibilidad completa.
- Las vistas de memoria creadas por NativeArena conservan su dirección/offset. Buffers directos externos se registran al recibirlos; no se demostró identidad de direcciones entre duplicados externos creados fuera del puente. Las direcciones de memoria virtual deben traducirse al conectar gráficos, audio o Bullet. El chequeo de vida del segmento no convierte un ByteBuffer ya entregado en un buffer con scope: la invalidación de esas vistas al cerrar un Arena sigue pendiente.
- El logger conserva nivel, handlers locales y propagación; ConsoleHandler aplica Formatter y el filtro de nivel. Chrome verifica handlers sin propagación y filtrado. No se implementó toda la configuración/infraestructura JUL ni bundles de mensajes. Paquetes AOT sin manifest asociado devuelven versiones null, permitidas por el contrato.
- Los adaptadores opcionales de Prometheus para OpenTelemetry se sustituyen por error explícito si se seleccionan. Los tipos Span ausentes siguen ausentes; no se crea un tracer falso ni se afirma que hubo exportación de telemetría.
- FileChannel.map, durabilidad automática de rws/rwd y nativas de mundo, física, audio y plataforma siguen pendientes. La base SQLite del puente no demuestra compatibilidad con partidas reales.

## Dependencias y reproducibilidad

`scripts/prepare_teavm.py` conserva el parche de caché de reflexión de la tarea 3 y genera el parche de monitor desde el source jar oficial TeaVM 0.16.0, SHA-256 `da6f83c1436c87a9ad683b6143aaa9c172b08c3974c9a7d5741a479d0d60092e`. El backend de metadata de campos también recibe un parche desde el source jar core ya fijado: un campo anotado sin Signature conserva su anotación y el genericType nulo, que Field.getGenericType resuelve al tipo raw. Una fixture Chrome comprueba ese caso y otro campo List<String>.

El constructor de vtables también recibe una corrección: una interfaz marker que ya resolvió a una clase no debe fusionar esa clase dentro de otra interfaz. Sin ella, el main llegaba a reemplazar la tabla de Object por la interfaz JNA Reboot y fallaba al emitir metadata. CompilerRegressionTest reproduce esa fusión con una jerarquía propia válida; otra prueba ejecuta su módulo en Chrome. El emisor conserva sus reglas originales y registra el representante de Object. No se modifica la jerarquía del juego. Las fuentes Apache-2.0 generadas y su licencia quedan en target ignorado; no se modifica el jar de Maven. El entorno local usa `-Xmx20g -Xss16m` para alojar también los bloques Wasm anidados del main completo. La inicialización de reflexión se emite en funciones por clase, llamadas en el orden original: el primer Wasm completo tenía una función de 9.245.402 bytes y Chrome la rechazó por superar su máximo de 7.654.321. La división conserva las mismas anotaciones, campos, métodos y tipos genéricos; no elimina registros Lua.

Las intrinsics estáticas nativas que necesitan referencias de función por reflexión reciben un cuerpo que usa la misma intrinsic inline. La prueba invoca reflectivamente las seis operaciones de bits/aritmética unsigned de Integer y Long, incluidos valores con bit alto y cero para CLZ/CTZ. La policy contrasta las firmas públicas de clases java/javax con el JDK 25 instalado, mediante PlatformClassLoader sin inicialización. Así excluye ampliaciones internas de TeaVM inexistentes en el JDK, como Object.getObjectClassInfo y constructores de Field/Method/Constructor con structs internos. Los tipos sin resolver conservan el nombre de API real para no ocultar diagnósticos. Las clases y miembros del juego no pasan por ese filtro; el manifiesto Lua completo se conserva. La fixture comprueba también que Field, Method y Constructor no expongan esos constructores internos. **Límite observado:** la división unsigned por cero produce una trampa Wasm `RuntimeError`, no una `ArithmeticException` atrapable en Java; la prueba Chrome registra ambos tamaños de entero. Esa traducción de excepciones de TeaVM queda pendiente.

`scripts/sqlite-lock.json` fija SQLite 3.54.1, archivo oficial sqlite-wasm-3540100.zip y SHA3-256 `87e24f6a4588692310b7942dc2fa7c7275bb9ba2e01d553e4115aa4a904a0050`. `scripts/prepare_sqlite.py` verifica el archivo y copia el loader y módulo a target ignorado. Fuente: [descargas SQLite](https://sqlite.org/download.html), [API Wasm OO1](https://sqlite.org/wasm/doc/trunk/api-oo1.md).

`tools/compatibility/JdkContracts.java` genera firmas de interfaces del JDK local y adaptadores JDBC con errores explícitos para métodos no implementados. `ApiUsage.java` registra nombres/firmas y lugares de uso, nunca cuerpos del juego. `scripts/wasm_stack.py` resuelve offsets de trazas contra nombres y límites de funciones del Wasm, sin desensamblarlo.

La validación del módulo completo encontró tipos de excepción usados solo en `catch` que TeaVM no denunciaba como ausentes. Se completaron InaccessibleObjectException, las excepciones JMX, MissingFormatArgumentException y UnsupportedClassVersionError con sus jerarquías y causas reales; las capturas dinámicas se verifican en Chrome. ObjectOutputStream conserva su jerarquía y rechaza serialización explícitamente. El backend ahora informa clases de catch ausentes como errores de compilación.

El análisis de tipos de pila respeta `forceNullable` para todos los resultados de referencia durante la transformación de corrutinas, incluidos casts, llamadas, bloques y `br_on_null`. Antes, una referencia restaurada nullable se entregaba a un bloque declarado non-null y Chrome rechazaba el módulo. La regresión compara ambos modos de inferencia para ramas, casts y bloques, y ejecuta cierres de recursos con suspensión mediante una interfaz, incluyendo un recurso nulo. La rama y el comportamiento Java se conservan.
